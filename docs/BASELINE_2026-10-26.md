The four markers that never run, with the reason for each:

| Markers | File | Why they do not run |
|--------:|------|---------------------|
| 2 | `kernel/src/ntg/simd/neon.rs` | `#[cfg(target_arch = "aarch64")]`; compiled only on ARM. Never executed on x86-64, and no ARM runner exists in CI. |
| 2 | `kernel/src/cuda/mod.rs` | The whole module is behind `feature = "cuda"` (off by default), and the two tests are also `#[ignore]` (need a GPU). |

**The `cuda` feature does not build.** `cargo test --release --features cuda --no-run` fails at
link time with undefined symbols `cuda_compute_agent_embeddings` and
`cuda_compute_policy_alignment`. `src/cuda/brain_delta.cu` and `brain_gamma.cu` exist, but there
is no `build.rs` and no `nvcc` step, so they are never compiled. Un-ignoring the tests on a GPU
machine is therefore not enough: the CUDA path is experimental and unbuildable until a build step
exists (this changes Phase B item B6).

Other crates: `backend/keymaster` has 6 markers and is tested by the CI job
"Keymaster backend (Rust)"; `dashboard` and `hostframe-backend` have none.

**The Oct 25 `updated_at` question.** No commit on any branch of this clone is dated 2026-10-24
or 2026-10-25 (`git log --all --since=2026-10-24 --until=2026-10-26`); the last commit on `main`
before 2026-10-26 is `929bee6` (2026-08-02). So the timestamp is not explained by pushed
commits. GitHub's events and insights are not readable from the tooling used here; the owner can
check Settings / Insights. Recorded as **unexplained**.

### What the whole-stack smoke covers (`scripts/smoke-whole.sh`, CI job `whole-stack`)

Covers: dashboard `/api/health`; keymaster `/health` and the dashboard seeing it; `kernel_host`
up; hostframe `/health`, `/ingest` (with the repo's sample payload) and `/metrics`;
`/api/classify`, `/api/score`, `/api/verify_ledger`; `/api/quad_brain`; `/api/hierarchy`
(10,000 nano agents); `/api/chat` only when Ollama is reachable (otherwise skipped).

Does **not** cover:
* the ternary x int8 GEMM, the int8 output-matrix kernel, the spinning pool or the C ABI:
  nothing in `kernel_host` or the dashboard calls them. They are covered by unit and
  integration tests (`ternary_i8_gemm`, `int8_gemm`, `spin_pool`, `ternary_i8_ffi`,
  `ternary_trained_mlp`) and by the `--check` mode of the three benchmarks;
* the external-backend path of `kernel_host` (`KEYMASTER_BACKEND_URL`): the smoke points that
  variable at the keymaster service but only sends intents that are answered locally. See
  [ADR 0012](architecture/0012-keymaster-contract.md): that path does not work against the
  keymaster service;
* anything on aarch64, with a GPU, or on Windows (the Windows release workflow has its own smoke).
